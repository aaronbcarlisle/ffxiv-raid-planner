# Stage 4 · RH1 — Recruiting home (lead side)

> Run with the `slice-loop` skill (`.claude/skills/slice-loop/`). Never load
> `superpowers:subagent-driven-development` in this repo.

**Goal:** a manager in V2 recruits end to end without opening Settings: one Recruiting page inside the static holds the applicant inbox (with the SF1 fit tier and reasons computed for each applicant), the listing editor and link invites. Listing status becomes real on the backend (paused and closed listings leave the Finder and stop requests) for both shells. V1 changes only by that fix and one label fix.

**Architecture:**
- **Task 1 (RH1a, backend only):** a pure `services/discovery_settings.py` (status normalisation + one `is_discoverable`) replacing the two router copies; the fit-input loader extracted from the discovery router into `services/finder_inputs.py`, batched by user id, so the join-request list can compute `fit` per applicant with the SF1 engine; the `join_requests` Player Hub item; the V1 `STATUS_LABEL` fix; a public release note.
- **Task 2 (RH1b, the riskiest):** the route `/group/:shareCode/recruit` under V2 (nested route, chrome prefix match, NewShell renders the page in place of `GroupViewContent`, Spine with no active tab, V1 redirects to the static), the page frame (header with the status `Select`, three URL-synced Tabs, the manager guard), and the seam: a redirect hook in `settingsPanelStore` that V2 registers so `open({tab: 'recruitment'})` never opens the dock, plus `hiddenTabs` on `SettingsPanel`.
- **Task 3 (RH1b):** the Applicants tab: `fit=true` in the store, third-person reason copy, the shared tier config and reason rows extracted from `FinderCard`, the applicant row with Accept / Decline / Under review / Link to roster, empty states.
- **Task 4 (RH1c):** the Listing tab (status card + hosted `DiscoveryTab`) and the V2 Invites tab.
- **Task 5 (RH1c):** entry points (`LeadingStaticRow`, `NotificationCenter`, Home's Recruiting line), the Needs-you item, and the doc flips that close Stage 4.

**PR split (planned now):** three stacked PRs. **RH1a** = Task 1, additive and mergeable alone (nothing sends `fit=true` until Task 3; enforcement is the public fix). **RH1b** = Tasks 2 + 3 (a page with a frame but no inbox is not shippable, so they merge together). **RH1c** = Tasks 4 + 5 + Finish write-backs. At Finish the controller measures each diff and keeps each PR under ~1,500 changed lines; if RH1b exceeds it, Task 3's `reasonCopy`/`ReasonRows` extraction moves to RH1a's tail as a refactor commit.

**Tech stack:** FastAPI (async SQLAlchemy, `CamelModel` schemas) · pytest + aiosqlite (`count_statements`, `tests/conftest.py:282-306`; golden `tests/golden/discovery_v1.json`) · React 19 · TypeScript · react-router (`useMatch`, `matchPath`) · Zustand · Vitest + Testing Library · ESLint design-system plugin.

**Spec (binding):** `design/redesign/specs/2026-09-27-recruit-home-design.md`: §2 (RH-1…RH-8), §3–§6, §7 (criteria 1–11), §8, §9. Also `CLAUDE.md` § UI rules, § Product rules and § Pitfalls (plugin contract, `n > 0 &&`, LF, `releaseNotes.ts` quoting, selector hooks for store reads).
