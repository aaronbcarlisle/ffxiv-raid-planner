## Rulings (bind every task)

- **R-P0-1 (`log_drop`, HS-35 #2 = 9A).** The handler keeps `membership = await require_membership(...)` and then checks, in this order, before any write:
  1. `membership.role == MemberRole.VIEWER` → `PermissionDenied("Viewers cannot log drops")`.
  2. `body.recipient_user_id` is set, differs from `current_user.id`, and `membership.role_level < ROLE_HIERARCHY[MemberRole.LEAD]` → `PermissionDenied("Only leads and owners can log a drop for another member")`. This mirrors `mount_farms.py:336-343`.
  3. `body.recipient_user_id` is set, and there is no `Membership` for it in this static with `role != VIEWER` → `HTTPException(400, "Recipient must be a member of this static")`. The precedent query is `collection_goals.py:246-250`. It runs **after** step 2, so a member can't probe who belongs to the static.
  - A drop with **no recipient** stays open to member and above. It changes nobody's state and can be deleted by its creator (`test_drop_without_recipient` `:287` stays green).
  - Admins get the virtual owner (`permissions.py:294-295`): they pass steps 1–2, and step 3 still applies.
- **R-P0-2 (`DELETE …/drops/{drop_id}`).**
  - New nullable column `reward_drop_log.recipient_prior_state String(10)`. `log_drop` sets it to the participant's state just before the flip, and only when the flip happens; otherwise it stays NULL.
  - One migration `l5m6n7o8p9q0_add_reward_drop_prior_state.py` with `down_revision = "k4l5m6n7o8p9"` (the current head). It follows the idempotent add-column pattern of `j3k4l5m6n7o8_add_users_is_admin.py:35-38`, and `downgrade` drops the column. Both `backend/scripts/check_migration_{heads,dialect}.py` must pass.
  - Route: `@router.delete("/static-groups/{group_id}/collection-goals/{goal_id}/drops/{drop_id}", status_code=204)`.
    - Viewer → 403.
    - The drop is loaded by `id`, `goal_id` and `static_group_id`; if it's missing → `NotFound` (404).
    - Allowed when `role_level >= LEAD` **or** `drop.created_by_id == current_user.id`. Otherwise → `PermissionDenied("Only leads, owners or the member who logged it can delete a drop")`.
  - **Restore rule (the result doesn't depend on delete order; V3).** Delete the row, then:
    1. If the deleted drop has a `recipient_prior_state` and other drops for the same `(goal_id, recipient_user_id)` remain, copy the prior onto the **earliest** remaining drop (by `created_at`, then `id`) that has none. The recipient stays "have", because they still received a drop.
    2. If no other drop remains, the deleted drop has a prior, and the participant row has `state == "have"`, set `state = prior` and `updated_at = now`. **Skip this** when the row's `last_synced_at` or `last_manual_override_at` is later than the drop's `created_at`: the plugin or a manual edit set the state since the drop, and that wins.
    - `source` and `last_manual_override_at` are not touched, because the flip didn't touch them either (`:651-662`).
  - `RewardDropResponse` gains `recipient_prior_state: str | None` (`recipientPriorState` on the client) for the confirm copy.
  - Frontend `collectionGoalStore.deleteDrop(groupId, goalId, dropId)` calls `api.delete`, removes the drop from local state, and refetches participants and goals. That mirrors `logDrop` (`:549-566`), which adds the drop locally rather than refetching drops (V15).

            for m in (getattr(rc.original_route, "methods", None) or ()) if m in MUTATING}
